    Remarks

    This component writes nothing to the rig. It only produces the pose that the three candidate driver spaces of the P2 spike consume, so that a difference in result between those spaces is attributable to the space itself.

    Phase advances in fixed steps of FixedStepHz, and the output is evaluated at the interpolated position between steps. Noise is therefore sampled at fixed intervals, so the motion does not change with frame rate. Physics-driven results still differ between machines; only this procedural layer is frame-rate independent.

    FlightHeight(float, float, float, float, float)

    L02 (run): vertical pelvis offset while both feet are off the ground, in metres above the neutral stance height — a true ballistic parabola over the analytic double-float window, not a reused walk-cycle wave, so it scales correctly with gravity alone (the low-gravity idea in locomotion-catalog.md's L02 note reuses this unchanged for a much longer flight phase). 0 outside that window, including whenever duty is at or above 0.5 (no flight phase exists) or legPhaseOffset is close enough to 0 or 1 that the two legs' stance windows would overlap rather than leave a clean gap — the ordinary case is legPhaseOffset 0.5, which this generalises correctly for any offset strictly between duty and 1 - duty.

    Derivation: a projectile launched at t=0 and landing at t=T follows y(t) = v0·t − ½g·t² with v0 = g·T/2 (solved from y(T)=0), which peaks at t=T/2 with height g·T²/8. Substituting the normalised progress τ=t/T gives the equivalent, simpler y(τ) = 4·peak·τ·(1−τ) used below.

    Bug fixed 2026-08-06 (user-reported: characters snapping several units upward for a moment when coming to rest, then reappearing in place — worse than, but visually similar to, the pre-existing "raycast hits own colliders" jitter). Neither Idle's nor the walk/run blend's own blend duration affected it, because the actual defect is here, not in either blend's timing: stepsPerSecond can be arbitrarily close to 0 for one or more frames while duty is still below 0.5 — eg while RunBlend.BlendDuration is still catching Duty Factor up to a walk value after a rapid stop — and cycleDuration below is 2 / stepsPerSecond, which is not a real "very long hang time" at that point, it is a division by near-zero. Unlike RemainingSwingSeconds(bool, float, float, float)'s identical-looking cycleDuration term, nothing here multiplies back by stepsPerSecond (or Move Speed) to cancel that growth, so it reached the pelvis directly as an unbounded jump. CodeSmile.AnyMotion.AnimateYourself.Gait.WalkGait.MinFlightCadence floors cycleDuration so it can no longer diverge, and fade then scales the now-bounded result smoothly to exactly 0 as stepsPerSecond itself drops towards 0, rather than leaving a small-but-fixed residual hop sitting at that floor. Both are pure safety guards, not authored values — genuine running cadence (the ordinary case whenever duty is deliberately below 0.5) never approaches them.

    GroundBlend(bool, float, float)

    L05: how much of the ground raycast's height correction IkTargetSpaceDriver.Apply should apply this frame, 0..1. 1 throughout stance, where PlantTarget already equals the animated position exactly. Ramps from 0 at the start of swing — where the prediction is farthest ahead of the animated position and least representative of where the foot currently, visually is — to 1 at its end, where the prediction converges onto the true touchdown point by construction (RemainingSwingSeconds(bool, float, float, float) reaches 0 there regardless of MoveSpeed). Applying the correction unblended reads as the foot snapping straight to a future footfall's height while still visually near the one it left — most visible crossing several closely-spaced height changes, eg stairs, where the predicted and current heights can differ by more than one step. Uses the same easing as the horizontal swing sweep so the two stay visually coherent.

    IsIdle(bool, float, float, float, float)

    Hard idle/walk decision (L04): true once the value that actually drives cadence falls below its threshold.     RemainingSwingSeconds(bool, float, float, float)

    L05 (foot planting on uneven ground): seconds of swing left for one leg, 0 during stance. One cycle is two steps, so its duration is 2 / stepsPerSecond; swing is the 1 - duty fraction of that. Feeds PlantTarget's forward lookahead — see the spec correction in locomotion-catalog.md §3. Floors the swing fraction at the same 0.02 the caller (EvaluateLeg(float, float, LegAsymmetry, float, float, Metrics, int, float, float)) floors its own swing-progress denominator at, so the two stay consistent right up to a duty authored close to 1 — otherwise swingT would already read as if swing were at least 2% of the cycle while this duration let it shrink smaller, disagreeing about how much swing is actually left.

    ResolveHandOffset(float, float, float, float)

    L11 (arm layering): where the hand sits for a given shoulder pose, as an offset from the shoulder joint in root space. This is the arm's IK target — the swing is a moving position, not a rotation, so that reaching for something is the same operation as swinging and the two can be blended without switching writers (arm-swing-spec.md §2).

    The composition is the same one HumanoidBoneSet.RotateAboutRootAxes applies and the same one Outward was re-measured against: spread outermost about the root's forward axis, pitch innermost about its right axis, from a hanging rest. Positive shoulderPitchDegrees puts the hand forward, positive spreadDegrees puts it outward.

    Reach is armChainLength times the cosine of half the elbow flexion, which is exact when the two arm segments are the same length and close otherwise. The driver solves with this rig's real per-side segment lengths, so whatever elbow angle that distance actually implies is what appears; this only has to produce a distance, not an angle.

    ResolveLateralCrossover(float, float, float)

    L06 (strafe): how far to shift each foot's lateral (X) position so the two are never closer than minSeparation — the crossover the catalog names ("the trailing foot must pass in front of or behind the leading foot, not through it"), resolved here as a minimum-separation floor rather than an actual fore/aft step-around (see MinLateralSeparation's own tooltip for that distinction). Symmetric about the pair's own midpoint, so neither foot is treated as more "correct" than the other, and correct regardless of which side is momentarily further left — a strafing sweep can put either foot on either side of the other. (0, 0) when already far enough apart. A pure function of both feet's positions, not a per-leg one, since the constraint is between them — called from Evaluate(float, float, float, float, Metrics, float) after both legs are resolved, never from EvaluateLeg(float, float, LegAsymmetry, float, float, Metrics, int, float, float) itself.

    ResolvePartialIdleTarget(Vector3, float)

    L04 low-hanging-fruit item 4 (idle-motion-spec.md §5): the idle target for a value that should only partially settle rather than snap fully to zero like every other idle-blended field. At partialWeight 1 this is UnityEngine.Vector3.zero, so ApplyIdle(ref GaitPose, float, float, Metrics, float, float, float)'s outer Lerp(value, target, idleWeight) reproduces the full-stop behaviour every field before this one already has. At 0 the target is value itself, so that outer lerp can never move it away from value regardless of idleWeight — the motion never stills. Values between are a partial settle. HeadSettleWeight is the only caller today; the mechanism is written generically in case a second field wants the same per-field override later.

    RunWeightTarget(bool, float, float, float, float, float, float)

    L02 (run): where the walk/run blend weight should be right now, purely as a function of current speed — 0 at or below the Min threshold, 1 at or above Max, eased in between with the same SmoothStep(InverseLerp(...)) construction CLAUDE.md already documents as the idiom for this.
